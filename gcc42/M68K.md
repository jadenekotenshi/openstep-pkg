# gcc42 on m68k-next-openstep4

Status: **work in progress.  The compiler proper (`cc1`, `cc1plus`, `cc1obj`,
`cc1objplus`) builds as a Linux cross compiler.  The assembly it produces is
accepted by the stock `as` on a NeXT 68k machine, and the self-checking C, C++
and Objective-C programs in `m68k-run` link and pass every check there, at `-O0`
and `-O2`.  Not done: the native bootstrap, libgcc and the C++ runtime library as
built by the package, exceptions, and `pkg test gcc42`.**

## What is there

- Apple's tree has the `m68k-*` entries in `gcc/config.gcc` but no
  `gcc/config/m68k` directory, as with SPARC.  `gcc-m68k-config-4.2.1.tar.gz`
  holds the FSF GCC 4.2.1 `gcc/config/m68k` files, unpacked over the source
  before the patch (see `sources`).
- `gcc/config.gcc`: `m68k-next-*` uses `nextstep.h m68k/next.h`, the shared
  Mach-O/NeXT code (`nextstep.c`, `nextstep-protos.h`) and `m68k/t-next`.
- `m68k/next.h` is the m68k counterpart of `i386/next.h` and `sparc/next.h`.  It
  is based on GCC 2.95.3's `m68k/next.h`, the last FSF version that supported
  NeXT's 68k machines (NeXT support was removed after that).
- `m68k/t-next` and `m68k/ARCH_INCLUDE.h` are the SPARC ones with the architecture
  name changed: the system headers are copied from
  `/NextDeveloper/Headers/*/m68k` to `include/*/__next_m68k__`.
- `gcc/final.c`: Apple's `MAX_CODE_ALIGN` was only defined where the target has an
  instruction `length` attribute, which the 4.2.1 m68k back end does not.
- `gcc42/build`, `test` pick the target from `arch(1)` (`GCC42_ARCH` overrides).
  The target is `m68k-next-openstep4`, like the other architectures (OPENSTEP 4.2 runs on the 68k machines).

## Choices made without a machine to check them on

- **Default CPU**: 68020 instructions, bit-fields and 68881/2 floating point,
  scheduled for the 68040 (`-m68020-40`), so the same code runs on a 68030+68882
  and on a 68040.  Like GCC 2.95 did.
- **MIT assembler syntax** (the m68k default, `movel a0@+,d0`), as the stock cc does.
- The frame pointer is spelled `a6`, not `fp` (4.2's `m68k.h` prints `fp`).
- Structures are returned as GCC always did on NeXT (`PCC_STATIC_STRUCT_RETURN`
  is not defined); `STRUCTURE_SIZE_BOUNDARY` is 16; stack boundary 32 bits.
- Case vectors are pc-relative `.word` tables in the text section, the form the
  4.2.1 `m68k.md` supports.  GCC 2.95's NeXT port used absolute tables in `.const`.
- Trampolines call `__enable_execute_stack`; the instruction cache is cleared
  with `trap #2` (both from GCC 2.95's port; not verified).
- Objective-C: the system runtime has no `objc_msgSend_stret` or
  `objc_msgSendSuper_stret` (a link of the first try said so), so
  `NEXTSTEP_STRUCT_VALUE_REGNUM` is defined, as on i386, to make messages with
  structure results use the ordinary messengers.  The address of the result is
  in `a1`, and `objc_msgSend` leaves it alone (`objctest.m` passes on a 68k machine).
- `TARGET_64BIT` is defined as 0 (Apple's Objective-C front end tests it).

## Apple's "cse of ZERO/SIGN EXTEND" is off on the 68k

Compiling `function.c` with the stage-1 compiler stopped with "unable to find a
register to spill in class 'ADDR_REGS'" on a push (`pea`) of a byte register
into a long stack slot.  Apple's tree has a local change to `cse.c` that files a
register holding a zero- or sign-extended memory load in the class of the
unextended load, so later uses of the long register can be replaced by the byte
register.  That is only valid where a byte register is part of the long one (x86,
PowerPC); on the 68k they are different registers and the replacement made
invalid insns.  `m68k/next.h` defines `CSE_EXTEND_OF_MEM` as 0, and `cse.c`
tests it.  It was found by compiling GCC's own sources with the Linux cross `cc1`
(95 of them compile at `-O2` now, with no internal compiler error); the same
dump flags, `-da`, show where an insn goes wrong.

To get the fix into a build that is already past the patch step (`GCC42_RESUME=1`
skips it) without rebuilding everything, apply only `m68k-cse-hotfix.patch` to
`gcc/cse.c` in the source tree and run make again: it rebuilds `cse.o`, relinks
the compiler and goes on.  A build started from scratch gets the same change from
the main patch.

## Checking the assembly

On a NeXT 68k machine, from `gcc42/m68k-asm`:

    sh check-asm.sh

assembles every sample `.s` (generated here by the cross `cc1`) with the stock `as`
and reports what it rejects.  `data.c` is also what to compare with the stock
`cc -S` output (`native-data.c` in `../sparc-asm` does this for SPARC).

## Running generated code

`check-asm.sh` only shows the stock assembler accepts the text.  In `m68k-run`,
`selftest.c` is a self-checking program (integers, long long, 68881 floating point,
varargs, structure passing and returning, switch tables, alloca, bit-fields,
printf).  `selftest-O0.s` and `selftest-O2.s` are what the cross `cc1` made of it
(`selftest.c` itself was checked with a host compiler first).  On a 68k machine:

    cd m68k-run && sh run-tests.sh

links each with the stock `cc` and runs it.  The stock cc's library has no
`__divdi3`, `__moddi3`, `__udivdi3`, `__fixdfdi` or `__floatdidf`, so
`m68k-run/libgcc/*.s` are the matching units of GCC's `libgcc2.c` (the 64-bit
integer, shift, compare and float conversion routines), compiled by the cross
`cc1` with the flags the libgcc build uses, one file per unit, and linked in.

C++ and Objective-C get the same treatment: `cxxtest.cc` (classes, virtual
functions, multiple inheritance, templates, operators, global constructors and
destructors; compiled with `-fno-exceptions -fno-rtti -fno-threadsafe-statics`
so it needs no C++ runtime library) and `objctest.m` (class and instance methods,
`super`, structure, `double` and `long long` returns, `Object` from the system
runtime), each with `-O0` and `-O2` assembly from the cross `cc1plus` and
`cc1obj`.  `run-tests.sh` runs all of them.  `cxxtest.cc` and `selftest.c` were
checked with a host compiler; `objctest.m` has no host equivalent here, so its
expected values were checked by reading and by running it on a 68k machine.

Exceptions need `libsupc++` and the sjlj unwinder, which need the system headers
and an m68k assembler to build, so they wait for the native bootstrap.

## Bootstrapping on the machine

`build` is the same three-stage bootstrap as the other architectures, with the
stock cc 2.7.2.1 as stage 0.  One m68k-specific step: the system library has no
`__divdi3`, `__moddi3`, `__udivdi3`, `__fixdfdi` or `__floatdidf`, which GCC's own
programs need, so `build` assembles `libgcc-stage0/*.s` (the same `libgcc2.c`
units as `m68k-run/libgcc`; the tarball is `gcc-libgcc-stage0-m68k.tar.gz`) into
`libgcc-stage0.a` and passes it as `LIBS` to configure.  Stages 2 and 3 use the
`libgcc.a` that stage 1 builds.  `GCC42_ULIMIT_D` (KB) overrides the 64 MB data
size limit if the compiler runs out of memory.

## What the 68k taught us (October 2026)

Found while bringing the dependencies of gcc42 up on a 68k machine with the
stock cc 2.7.2.1.  They apply to every package, not only gcc42.

- **The stock cc aborts at `-O0` on 64-bit-heavy code** ("cc: Internal compiler
  error: program cc1obj got fatal signal 6"; the stock cc compiles C with
  `cc1obj`): `tar` (`human.c`, `names.c`) and `wget-bootstrap` (`mktime.c`).
  `-O1` and up compile them.  `tar` now builds at `-O1` on every architecture
  (tested on x86 and SPARC); `wget-bootstrap` at `-O1` on m68k only.  The cause
  looks like register allocation running out of registers for functions with
  many `long long` values live at `-O0`; it only showed for whole functions
  (every part compiled alone).
- **The stock cc writes invalid assembly for some 64-bit arithmetic above
  `-O0`** ("instruction/operands mismatch -- Statement 'addl a2,a6@(-176)'",
  an add from an address register into memory): OpenSSL's `poly1305.c`.  It is
  built at `-O0`; `PKG_OPENSSL_O0_FILES` adds more files.
- **The stock cc segfaults on gnulib's `sha512.c`** at every level.  It is left
  out of `wget-bootstrap` (only Metalink uses it, and that is off).
- **The 68k libc compares bytes as signed in `memcmp()` and `strcmp()`**
  (`memcmp(0x80, 0x01)` is -129), as SPARC's does.  The `pkg_cmp_*` helpers in
  `build-helpers.sh` now apply on m68k.  This broke OpenSSL's object-identifier
  lookups (116 of 1065 not found) until `libcrypto` was built with them.
- **`pkg` needs a downloader that speaks TLS for `https` sources**, so a fresh
  machine builds `wget-bootstrap` (and `openssl`) before it can fetch gcc's
  sources.  Copying the two source tarballs into the package's source cache
  (`/usr/local/var/pkg/cache/sources/gcc42/`) skips that.

Finding the flags that work for one file: build with `--preserve-build-tree`,
then in the failing directory run the compile by hand (`gnumake V=1 <file>.o`
prints the real command) with different `-O...` options, as the loops in the
`tar` and OpenSSL discussions did.

## SPARC-specific code and the 68k

The 68k is big-endian like SPARC but does not trap on unaligned access (the
68020 and later), and its libc, libm and headers are not SPARC's.  How each
SPARC-only branch in the tree is expected to carry over; none of these has been
tried on a 68k yet except where noted:

| Package | SPARC branch | On m68k |
|---|---|---|
| `sdl12` | `-DSDL_BYTEORDER=4321` | needed (big-endian): now applied on m68k too |
| `build-helpers.sh` `pkg_cmp_*` | unsigned `memcmp`/`strcmp` | needed, confirmed: applied on m68k |
| `xxhash`, `zstd` | `MEM_FORCE_MEMORY_ACCESS=0` (unaligned reads fault) | not needed (68020+ allows unaligned access) |
| `quickjs`, `duktape`, `emacs` | alignment of 64-bit values, wide ints | probably not needed; `duktape` already knows the 68k byte order |
| `libgcrypt` | `-D__sparc_v8__` so `longlong.h` finds its division routine with `--disable-asm` | unknown: `longlong.h` has its own 68k branch (inline assembly); watch for an undefined `_udiv_qrnnd` or an assembler error |
| `ntp` | no NetInfo header; `sigsetjmp` mapped to `setjmp` | unknown: depends on the 68k headers and libc; watch for the same link errors (`_sigsetjmp`) |
| `gzip` | `deflate.c` compiled unoptimized (the SPARC cc aborts) | watch: the 68k cc may abort too (see above) |
| `git`, `python311` | `-O0` / `-O1` and `-fwrapv`, from a suspected gcc 4.2 miscompile | needs gcc42 first; start at the defaults, and remember the SPARC problems turned out to be libc comparisons |
| `python311` | own `ldexp()` (the SPARC libm returns 0 for subnormals) | unknown: `float.fromhex('0x0.0000000000001p-1022')` tests it |

## Likely trouble on the way to gcc42

gcc42 depends on `make`, `tar`, `coreutils`, `patch`, `texinfo`, `gawk`, `m4`,
`bison`, `flex` and `grep`, plus `pdksh` and `gzip` (and `wget-bootstrap` for the
downloads).  Judging by how many of their C files use 64-bit types, and by the
files that have already failed:

- Most at risk: `texinfo` (gnulib's `vasnprintf.c`, `printf-parse.c`,
  `printf-args.c`), `gawk` (`builtin.c`, `floatcomp.c`), `grep` (`strtoull.c`,
  `xstrtoumax.c`, `grep.c`), and `m4`/`bison`/`flex`/`make` if their gnulib
  includes `mktime.c`, `sha*.c` or `strtoll`.  The expected symptom is the
  `cc1obj` abort or segfault; the expected fix is `-O1` (or `-O0`, whichever the
  loop shows) for that one object.
- Lower risk: `pdksh` and `gzip` use no 64-bit types in their C files; `patch`
  has one (`memchr.c`).
- `coreutils` uses `uintmax_t` throughout and has already built on the 68k.
